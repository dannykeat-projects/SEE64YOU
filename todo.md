# SEE64YOU work queue

Scope: [Product](docs/PRODUCT.md). Procedures: [Testing](docs/LOCAL_TESTING.md). Completed investigations and receipts remain in Git history and private build artifacts.

## Current baseline

Alpha.8 uses the ten-file SYSTEM layout and stores ordinary documents in SEE64YOU/docs/; settings, keys, recovery and journals remain at the root. First Save handles the Ultimate missing-directory status and creates docs. Host regressions, SD/USB fit/manifests, matching VICE and bounded SD hardware acceptance pass; remaining gates are below.

Save replacement/rollback, batched loading, resident reserve recovery and numbered selectors are implemented. Exact-package SD checks cover Editor recovery and Publisher uploads; native key/network failure injection remains open. These results do not establish comparable loading gains.

### Editor — sustained slowdown after inserting and deleting text (P1)

**Observed 24 November 2026:** A new document initially felt responsive. After typing a full screen, deleting it and returning to the top to type a short paragraph, sustained typing felt very laggy despite the small remaining document. This is distinct from large-document benchmarks; cause unverified.

- [ ] **Reproduce before editing.** Record firmware, input device, wrap state, program/overlay hashes, document length/shape and deletion method. In a disposable copy, measure initial typing, add roughly one screen of text, select/delete it, return to top and measure first/subsequent keystrokes. Test mouse/MARK selection and ordinary deletion where applicable; compare a freshly opened byte-identical document at the same cursor/wrap state. Repeat undo/redo and insert/delete cycles. Separate first-key pause from sustained latency; capture median/worst cases and exact final source. If reopening resets slowdown, identify which state was reset rather than assuming a cause.
  - **Evidence 25 Nov 2026 (host REU model, branch codex/local-model-experiment):** Reproduced with the production sources (`buffer_reu.c clipboard.c history_reu.c editor.c document.c charset.c`, `-DS64_REU_BUFFER=1 -DS64_INDEPENDENT_EDITOR=1`, counters around `s64_reu_load`/`s64_reu_store`). The naive post-delete models do not reproduce lag: typing at the top of a 64-byte document after deletion measured 0 loads / 1 store per keystroke (fresh open at the same cursor was 3 loads / 42 bytes per keystroke), and re-typing the first 100 characters of an emptied document showed ~0 loads per keystroke. The sustained cost appears while typing one long *logical* line, which is what a wrapped paragraph is while RETURN is never typed: 1,200 keystrokes producing a single 1,200-character line cost 117,053 loads / 7,384,617 bytes loaded, concentrated in single-keystroke bursts (worst keystroke 99,433 loads / 6,270,976 bytes, next 17,620 loads / 1,127,680 bytes) with ~0 loads on the following keys; the identical keystrokes broken by a newline every 40 characters cost 9,756 loads / 600,730 bytes. Cost therefore tracks current logical-line length, not remaining document size, which matches "small remaining document" plus "sustained typing felt very laggy", and a freshly opened document with short lines hides it. Firmware, input device and overlay hashes remain C64U-gated and unrecorded.
- [ ] **Localize the bottleneck.** Reuse host/VICE counters and hardware timing fixtures. Compare REU gap position/movement/transfers, history occupancy/coalescing, logical cursor/viewport caches, selection invalidation, wrap/reflow, render hot-path eligibility and overlay load frequency before/after deletion. Trace event/render paths in `buffer_reu.c`, `editor.c`, `ui.c` and resident/overlay entries. Check existing performance changes on main. Prefer a focused evidence-based fix; no history reset, background autosave, broad renderer rewrite or new overlay merely to mask the symptom.
  - **Localized 25 Nov 2026 (host):** `s64_buffer_char_at` reuses the cached 64-byte window only while the requested physical address is inside `[reu_window_start, reu_window_start + reu_window_length)`, and `load_window` started the window at exactly the requested address, so every step to a lower address reloaded a full window: one `s64_editor_internal_line_start` over a 1,200-character logical line measured 1,200 loads / 76,800 bytes (64x byte amplification), and MARK + home navigation over the same line measured 2,400 loads / 153,600 bytes. The Editor wrap/viewport helpers walk characters with that call on each keystroke (`s64_editor_internal_line_start` `editor.c` 20, `line_end` 31, `wrapped_row_at` 69, `previous_wrapped_row_start` 92, `s64_editor_ensure_cursor_visible` 683 word-wrap branch), which is where the bursts concentrate at scroll boundaries. History/undo measured 1 store per keystroke and a 16-level ring with per-entry metadata caches (`history_reu.c`), so history is ruled out as the sustained cost. The repository's own `tools/test_editor_performance.py` already isolates the same factor: `single_long_line end_of_line_midpoint` 13,079 loads for 1,024 characters versus 39 loads for `lines_40_columns`.
  - **Fix 25 Nov 2026 (host):** page-aligned the cached character window in `load_window` (`start = physical & ~(S64_REU_WINDOW_SIZE - 1u)`, transfer length clamped to remaining capacity), so neighbouring `char_at` steps reuse one transfer. Four lines, no new state, the `char_at` bounds test and the separate `s64_buffer_read`/`s64_buffer_find_byte`/`move_gap` transfer paths are untouched (those call `invalidate_window` first). Added a deterministic case to `client/tests/reu_buffer_test.c`: forward and backward `s64_buffer_char_at` scans over 300 bytes return the identical source bytes and need at most 8 window transfers; compiled against the committed window it fails there (`FAIL: backward window scan transfers one window per 64 characters`, 300 transfers), so the case is a real regression test. `tools/test_editor_performance.py` measured before/after on identical inputs: 1,024-character `single_long_line end_of_line_midpoint` 13,079 loads / 828,831 bytes -> 588 loads / 29,407 bytes; 16,384-character `paste_64_midpoint` 176,680 loads / 11.20 MB -> 7,360 loads / 366,763 bytes; 60,000-character `end_of_line_midpoint` 1,345,687 loads / 85.35 MB -> 55,486 loads / 2,777,346 bytes (24x fewer loads, 31x fewer bytes). `insert_midpoint` rows are unchanged (35 / 357 / 1,244 loads), so gap relocation and correctness are unaffected, and a scratch harness confirms byte-exact readback plus `char_at` agreement for all 1,200 typed characters across window boundaries.
  - **Gates 25 Nov 2026:** passed - full `tools/validate.sh --host-only` suite stays green (exit 0, 90+ groups) after the change, including the new window case, and `tools/test_editor_performance.py` completes; failed/blocked here - the C64-target Editor link gates do not build under this environment's plain `STORAGE_ROOT=/Usb0/` configuration at either revision: `independent-editor` overflows CODE/MAIN by 2,769 bytes at HEAD and 2,779 bytes now, and `editor-overlay-fit` overflows BSS by 498 -> 508 bytes with MODEL_CODE 2,716, FILE_RODATA 276 and PUBLICATION_CODE 2,339 unchanged, so the change costs 10 bytes of resident code and the >=1,024-byte Editor reserve must be re-measured on the verified shipping build configuration (SD/USB mounts, overlay selection) - recorded as unverified, not a regression introduced here; unverified - VICE jiffies, physical C64U latency for the reported sequence, screen-fit and the documented size/drag benchmarks.
- [ ] **Regression and acceptance.** Add deterministic post-delete regression with identical source/cursor results and operation counts; compare sustained typing with fresh equivalent state without regressing undo/redo, selection, wrapping, save/reopen or recovery. Rerun affected host/VICE checks, SD/USB fit/manifests and matched physical C64U tests for reported sequence and existing size/drag benchmarks. Preserve resident reserve, recovery and restoration guards. Record measured improvement, remaining first-key latency and unverified gates; update user docs only for actual behavior changes.
  - **Partial work 25 Nov 2026:** the deterministic host regression above is added inside the existing `client/tests/reu_buffer_test.c` gate (byte-identical scans plus a bounded transfer count), and `tools/test_editor_performance.py`, the REU buffer/clipboard/history groups and the whole host suite were rerun after the change with the improvement recorded.
